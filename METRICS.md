# TopsWatch Metrics Reference

All metrics are exposed at `/metrics` in Prometheus format and as JSON via the
SSE/history APIs. Metric names are auto-generated by appending a unit suffix to
`topswatch_<module>_<metric>`:

| Unit  | Suffix      |
|-------|-------------|
| `%`   | `_percent`  |
| `MHz` | `_mhz`      |
| `W`   | `_watts`    |
| `C`   | `_celsius`  |
| `MB/s`| `_mbps`     |
| `bytes`| `_bytes`   |
| (none)| (no suffix) |

A metric is only reported when its source is readable. Missing hardware,
missing drivers, or insufficient permissions cause individual metrics to be
silently omitted from a sample — the rest still publish.

In paths below, `*` is a `glob(3)` wildcard and `<slot>` is the discovered PCI
slot for the device (e.g. `0000:00:0b.0`).

---

## CPU

### `topswatch_cpu_info`
- **Source:** `/proc/cpuinfo`
- **Unit:** gauge=1 (info metric)
- **Description:** Static CPU identification. Labels: `model`, `vendor`, `cores` (physical), `threads` (logical), `arch`.

### `topswatch_cpu_utilization_percent`
- **Source:** `/proc/stat` (first line beginning `cpu `)
- **Unit:** %
- **Description:** Aggregate CPU busy ratio across all logical cores, computed as Δ`(total - idle - iowait) / total` between samples and clamped to 0–100. Matches `top`'s `%Cpu(s):` summary line.

### `topswatch_cpu_cores_used`
- **Source:** `/proc/stat` (first line beginning `cpu `)
- **Unit:** cores (no suffix)
- **Description:** Same delta as `utilization`, multiplied by the logical thread count. Irix-style "how many cores are busy" — matches the denominator of `top`'s per-process `%CPU` column. A 22-thread CPU pegged on every core reads 22.0.

### `topswatch_cpu_frequency_mhz`
- **Source:** `/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq` (kHz, averaged across all matching files)
- **Unit:** MHz
- **Description:** Mean current frequency across all logical CPUs.

### `topswatch_cpu_power_watts`
- **Source:**
  - `/sys/class/powercap/intel-rapl:N/energy_uj` (microjoules)
  - Zone selected by reading `/sys/class/powercap/intel-rapl:N/name` and requiring it to start with `package-`
  - Wrap range from `/sys/class/powercap/intel-rapl:N/max_energy_range_uj`
- **Unit:** W
- **Description:** CPU package power via Intel RAPL, computed as Δenergy / Δtime. Often requires root after CVE-2020-8694; metric is omitted if `energy_uj` is unreadable.

### `topswatch_cpu_core_utilization_percent`
- **Source:** Per-CPU `cpuN ...` lines in `/proc/stat` (one line per logical CPU visible in our cgroup)
- **Unit:** %
- **Description:** Per-logical-CPU busy fraction, computed as Δ`(total - idle - iowait) / total` between samples and clamped to 0–100. Carries labels `core` (logical CPU id, e.g. `"0"`) and `core_type` (`performance`, `efficient`, or `low_power`). Aggregate `topswatch_cpu_utilization_percent` is unchanged and still emitted alongside.

### `topswatch_cpu_core_frequency_mhz`
- **Source:** `/sys/devices/system/cpu/cpuN/cpufreq/scaling_cur_freq` (kHz)
- **Unit:** MHz
- **Description:** Current frequency for one logical CPU. Same `core` and `core_type` labels as `core_utilization`. Aggregate `topswatch_cpu_frequency_mhz` (the mean across all cores) is unchanged and still emitted alongside.

### Hybrid CPU classification

The `core_type` label is derived once at startup as follows:

1. Read `/sys/devices/cpu_core/cpus` — every logical CPU listed here is `performance`.
2. Read `/sys/devices/cpu_atom/cpus` — for each CPU listed there, read `/sys/devices/system/cpu/cpuN/cpufreq/cpuinfo_max_freq`. The CPU(s) with the highest max frequency are `efficient`; any with strictly lower max frequency are `low_power`.
3. Visible CPUs not in either PMU set, or systems with no `cpu_core`/`cpu_atom` dirs at all, fall back to `performance`.

This handles 2-tier hybrids (Alder Lake / Raptor Lake / Meteor Lake — all atoms have the same max freq, so they all get `efficient`) and 3-tier hybrids (Panther Lake — LP-E cores have a lower `cpuinfo_max_freq` than the regular E-cores, so they bin into `low_power`) with the same code path. There is no kernel `core_type` sysfs file on the kernels we've tested; the max-freq heuristic is the most reliable signal available.

"Visible" means listed in `/proc/stat` — inside an LXC container with a cgroup `cpuset`, this is only the cores assigned to the container even though the global sysfs paths exist for all logical CPUs on the host.

### `topswatch_cpu_temperature_celsius`
- **Source:**
  - First hwmon device whose `/sys/class/hwmon/hwmon*/name` is one of `coretemp`, `k10temp`, or `zenpower`
  - Then `/sys/class/hwmon/hwmon*/temp1_input` on that device (millidegrees)
- **Unit:** °C
- **Description:** CPU package temperature. On Intel `coretemp` this is the package sensor; on AMD `k10temp` this is Tctl/Tdie.

## GPU

Discovered by scanning `/sys/class/drm/card*/device/vendor` for Intel vendor ID
`0x8086` and verifying `/sys/class/drm/card*/device/class` starts with `0x03`
(display controller). Two driver paths are supported: the modern `xe` driver
(preferred) and the legacy `i915` driver (fallback). The kernel driver is read
from the `/sys/class/drm/card*/device/driver` symlink.

In the paths below, `<card>` is the discovered DRM card (e.g. `card0`) and
`<hwmonN>` is the first entry under `/sys/class/drm/<card>/device/hwmon/`.

### `topswatch_gpu_info`
- **Source:**
  - `/sys/class/drm/<card>/device/vendor`
  - `/sys/class/drm/<card>/device/device`
  - `/sys/class/drm/<card>/device/driver` (symlink)
- **Unit:** gauge=1 (info metric)
- **Description:** Static GPU identification. Labels: `pci_id`, `driver` (`xe` or `i915`), `pci_slot`, `card`.

### `topswatch_gpu_utilization_percent`
- **Source:** `perf_event_open(2)` against the GPU's kernel PMU. Two driver paths:
  - **Xe driver:** PMU at `/sys/bus/event_source/devices/xe_<slot>/`. Opens two counters per engine: `engine-active-ticks` and `engine-total-ticks`, with per-engine config packed via `format/` bit fields (`engine_class`, `engine_instance`, `gt`). Engines discovered from `/sys/class/drm/card*/device/tile*/gt*/engines/`. Busy fraction per engine = Δactive / Δtotal (naturally normalized, no wall-time needed).
  - **i915 driver:** PMU at `/sys/bus/event_source/devices/i915/`. One pre-baked event per engine (e.g. `events/rcs0-busy`). Counter reads as busy nanoseconds; busy fraction = Δbusy_ns / Δwall_ns.
  - Aggregate utilization = Σ per-engine fractions, clamped to 100%.
- **Unit:** %
- **Description:** Aggregate GPU busy fraction across all engines. Uses the same kernel PMU that `intel_gpu_top` reads, accessed via raw `perf_event_open(2)` (no CGO). Typically requires `CAP_PERFMON` or root unless `perf_event_paranoid` is set permissively.

### `topswatch_gpu_engine_busy_percent`
- **Source:** Same `perf_event_open` fds as `topswatch_gpu_utilization_percent`, reported per engine
- **Unit:** %
- **Description:** Per-engine busy fraction. One time series per engine, distinguished by the `engine` label (e.g. `rcs0`, `bcs0`, `vcs0`, `vecs0`, or whatever engines the kernel exposes for the detected GPU).

### `topswatch_gpu_memory_used_bytes`
- **Source:** `/proc/<pid>/fdinfo/<fd>` for every open `/dev/dri/*` client. Memory is the sum of the per-region `drm-total-<region>` keys; the workload class comes from the client's cumulative `drm-cycles-<engine>` counters (`ccs` → compute, `rcs` → graphics, `vcs`/`vecs` → video; `bcs` carries no signal and is ignored). Clients are deduped by `drm-client-id`, since a process that `dup(2)`s its device fd reports the same buffers once per fd.
- **Unit:** bytes
- **Description:** GPU memory held by DRM clients, grouped by the `class` label: `compute`, `graphics`, `compute+graphics`, `video`, or `idle`. One series per class is emitted on every sample, zero included, so a class going quiet reads as 0 rather than a frozen last value; sum across the label for the device total. This is the Intel analogue of `nvidia-smi`'s per-process memory plus its `C`/`G`/`C+G` type column — the class describes the client, not the pages, as the hardware has no separate graphics and compute pools. On an integrated GPU there is no VRAM, so this is system RAM the GPU has mapped. See `evidence/gpu_memory_used_bytes.md`.

### `topswatch_gpu_frequency_actual_mhz`
- **Source:**
  - Xe: `/sys/class/drm/<card>/device/tile*/gt*/freq0/act_freq`
  - i915: `/sys/class/drm/<card>/gt_act_freq_mhz`
- **Unit:** MHz
- **Description:** Currently observed GT clock.

### `topswatch_gpu_frequency_requested_mhz`
- **Source:**
  - Xe: `/sys/class/drm/<card>/device/tile*/gt*/freq0/cur_freq`
  - i915: `/sys/class/drm/<card>/gt_cur_freq_mhz`
- **Unit:** MHz
- **Description:** Software-requested GT clock. May differ from actual when the GPU is throttling.

### `topswatch_gpu_frequency_min_mhz`
- **Source:**
  - Xe: `/sys/class/drm/<card>/device/tile*/gt*/freq0/min_freq`
  - i915: `/sys/class/drm/<card>/gt_min_freq_mhz`
- **Unit:** MHz
- **Description:** Configured lower bound for the GT clock.

### `topswatch_gpu_frequency_max_mhz`
- **Source:**
  - Xe: `/sys/class/drm/<card>/device/tile*/gt*/freq0/max_freq`
  - i915: `/sys/class/drm/<card>/gt_max_freq_mhz`
- **Unit:** MHz
- **Description:** Configured upper bound for the GT clock.

### `topswatch_gpu_frequency_rp0_mhz`
- **Source:**
  - Xe: `/sys/class/drm/<card>/device/tile*/gt*/freq0/rp0_freq`
  - i915: `/sys/class/drm/<card>/gt_boost_freq_mhz`
- **Unit:** MHz
- **Description:** Hardware-capable maximum (boost) frequency. Carries label `desc="maximum capable"` (Xe) or `"boost"` (i915).

### `topswatch_gpu_frequency_rpe_mhz`
- **Source:** Xe only: `/sys/class/drm/<card>/device/tile*/gt*/freq0/rpe_freq`
- **Unit:** MHz
- **Description:** Most power-efficient operating frequency. Carries label `desc="efficient"`.

### `topswatch_gpu_frequency_rpn_mhz`
- **Source:**
  - Xe: `/sys/class/drm/<card>/device/tile*/gt*/freq0/rpn_freq`
  - i915: `/sys/class/drm/<card>/gt_RPn_freq_mhz`
- **Unit:** MHz
- **Description:** Hardware-capable minimum frequency. Carries label `desc="minimum capable"`.

### `topswatch_gpu_temperature_celsius`
- **Source:** First available of:
  - `/sys/class/drm/<card>/device/hwmon/<hwmonN>/temp1_input`
  - `/sys/class/drm/<card>/device/hwmon/<hwmonN>/temp2_input`
  - (millidegrees; sensor name from sibling `temp{1,2}_label` if present)
- **Unit:** °C
- **Description:** GPU temperature. The `sensor` label is taken from the matching `*_label` file, or `package` if absent.

### `topswatch_gpu_power_watts`
- **Source:**
  - `/sys/class/powercap/intel-rapl:N:M/energy_uj` for the sub-zone whose `name` file is `uncore` (microjoules)
  - Wrap range from `/sys/class/powercap/intel-rapl:N:M/max_energy_range_uj`
- **Unit:** W
- **Description:** GPU power computed as Δenergy / Δtime, read from the Intel RAPL "uncore" power domain. On Intel client SoCs the uncore zone is dominated by the integrated GPU (it also includes the package interconnect and L3 slice, so expect a small non-zero baseline at idle). Used because `xe_hwmon` is not implemented for current-gen Xe driver. Often requires root after CVE-2020-8694; the metric is omitted if `energy_uj` is unreadable.

Frequency metrics that don't exist on a given driver/SKU are omitted. If
hwmon is absent (common on current integrated GPUs) the temperature metric
is simply not published.

## NPU

Discovered by walking `/sys/bus/pci/drivers/intel_vpu/<slot>/`, where `<slot>`
is the PCI bus address of the bound NPU device. The CPU generation is derived
from `/sys/bus/pci/drivers/intel_vpu/<slot>/device`:

| PCI ID  | Generation   |
|---------|--------------|
| `7d1d`  | Meteor Lake  |
| `ad1d`  | Arrow Lake   |
| `643e`  | Lunar Lake   |
| `b03e`  | Panther Lake |

Sysfs metrics work on every supported generation. PMT-sourced metrics
require a matching telemetry GUID under `/sys/class/intel_pmt/telem*/` and
generation-specific register offset tables; if PMT discovery fails (unknown
generation, missing GUID, or permission errors on the `telem` blob), the PMT
metrics are silently disabled and only sysfs metrics are published.

### `topswatch_npu_info`
- **Source:**
  - `/sys/bus/pci/drivers/intel_vpu/<slot>/device`
  - `modinfo -F version intel_vpu` (driver version)
  - `/sys/kernel/debug/accel/*/fw_version` (firmware version)
- **Unit:** gauge=1 (info metric)
- **Description:** Static NPU identification. Labels: `pci_id`, `generation`, `driver` (intel_vpu version), `firmware`.

### `topswatch_npu_utilization_percent`
- **Source:** `/sys/bus/pci/drivers/intel_vpu/<slot>/npu_busy_time_us`
- **Unit:** %
- **Description:** Fraction of wall-clock time the NPU was busy between samples. Computed as Δbusy / Δwall, clamped to 0–100.

### `topswatch_npu_memory_used_bytes`
- **Source:** `/sys/bus/pci/drivers/intel_vpu/<slot>/npu_memory_utilization` (Panther Lake and later only)
- **Unit:** bytes
- **Description:** NPU memory in use. Omitted on generations that don't expose this file.

### `topswatch_npu_memory_total_bytes`
- **Source:** `MemTotal:` line of `/proc/meminfo` (read once at startup)
- **Unit:** bytes
- **Description:** Capacity denominator for `memory_used`. On integrated NPUs (Panther Lake and earlier) the NPU has no dedicated VRAM and shares system RAM, so the right denominator is the host's `MemTotal`. Emitted only when `memory_used` is also available so the dashboard can render a percentage.

### `topswatch_npu_memory_used_percent`
- **Source:** Derived: `memory_used` / `memory_total` × 100
- **Unit:** %
- **Description:** Convenience metric so consumers don't have to compute the ratio. Capped at 100. Emitted only when both `memory_used` and `memory_total` are present. The `npu_memory_pressure` warning rule fires when this exceeds 80% for 10 seconds.

### `topswatch_npu_frequency_mhz`
- **Source:** `/sys/class/intel_pmt/telem*/telem` (entry matched to a known NPU GUID), `VPU_WORKPOINT` register, bits [7:0] (PLL ratio)
- **Unit:** MHz
- **Description:** NPU DPU operating frequency, converted from the PLL ratio via a generation-specific formula derived from the kernel's `ivpu_hw_btrs.c`:
  - Meteor Lake / Arrow Lake: `ratio × 50 MHz × 2/3` (kernel `pll_ratio_to_dpu_freq_mtl`)
  - Lunar Lake / Panther Lake: `ratio × 50 MHz / 2` (kernel `pll_ratio_to_dpu_freq_lnl`)

### `topswatch_npu_power_watts`
- **Source:** `/sys/class/intel_pmt/telem*/telem` (NPU GUID), `VPU_ENERGY` register (cumulative, U18.14 fixed-point joules, confirmed by Intel PMT XML `tenergy` datatype)
- **Unit:** W
- **Description:** NPU power computed as Δenergy / Δtime. Energy is model-estimated by Pcode using utilization factor from the VPU. Requires two samples to publish.

### `topswatch_npu_temperature_celsius`
- **Source:** `/sys/class/intel_pmt/telem*/telem` (NPU GUID), `SOC_TEMPERATURES` register, bits [47:40]
- **Unit:** °C
- **Description:** NPU SoC temperature.

### `topswatch_npu_ddr_bandwidth_mbps`
- **Source:** `/sys/class/intel_pmt/telem*/telem` (NPU GUID), `VPU_MEMORY_BW` register (cumulative counter in kilobytes, PMT datatype `tbw_KB`)
- **Unit:** MB/s
- **Description:** DDR bandwidth observed by the NPU, computed as ΔKB / 1000 / Δtime. Requires two samples to publish (delta-based, like power). The web UI displays this as GB/s.

### `topswatch_npu_tile_config`
- **Source:** `/sys/class/intel_pmt/telem*/telem` (NPU GUID), `VPU_WORKPOINT` register, bits [23:16]
- **Unit:** (count, no suffix)
- **Description:** Active NPU tile configuration. Unitless integer.

## History Tiers

`/api/metrics/history?range=<tier>` returns chronological samples from one of three downsampled rings. The available tier names are:

| Range value | Resolution | Capacity | Time span |
|---|---|---|---|
| `5min` (default) | 1 second | 300 | 5 minutes |
| `1h`             | 10 seconds | 360 | 1 hour |
| `24h`            | 5 minutes | 288 | 24 hours |

Each tier is its own ring buffer. New samples from the live collector are folded into the open bucket of every tier on every collection tick. When a bucket's window has elapsed (1s, 10s, or 5min), the running average of the metrics in that bucket is committed to the ring and a new bucket starts. Metrics are averaged within a bucket — for gauges and rate metrics this is meaningful; for counters topswatch already converts to rates before publishing, so this is fine for everything we expose.

`?range=` is also surfaced via `/api/metrics/ranges`, which returns a JSON array of tier names in display order. The dashboard exposes a tier dropdown in the header and re-fetches when it changes.

History tiers contain only `timestamp` and `metrics` (no processes, warnings, or device info). Live data — `/api/metrics/latest` and `/api/metrics/stream` — still carries everything.

## Warnings

In addition to metrics and processes, each sample carries a list of currently-active
warnings under the `warnings` field of `/api/metrics/latest` and the SSE stream.
Warnings are derived server-side from the metrics already collected; no new
data sources are introduced. Each warning has the shape:

```json
{
  "module":   "cpu" | "gpu" | "npu",
  "kind":     "thermal" | "throttle" | "memory",
  "severity": "warning" | "critical",
  "message":  "human-readable string",
  "since":    "RFC3339 timestamp of when the condition first became true"
}
```

A warning only appears once its underlying condition has been continuously
true for the rule's `duration`. It disappears the moment the condition
becomes false (no hysteresis). Warnings are stripped from
`/api/metrics/history` since the dashboard only ever shows "now".

### Active rules

| Rule id | Module | Kind | Severity | Sustained for | Trigger |
|---|---|---|---|---|---|
| `cpu_temp_warning`  | cpu | thermal | warning  | 10s | `temperature` ≥ 90 °C |
| `cpu_temp_critical` | cpu | thermal | critical | 0s  | `temperature` ≥ 95 °C |
| `npu_temp_warning`  | npu | thermal | warning  | 10s | `temperature` ≥ 90 °C |
| `npu_temp_critical` | npu | thermal | critical | 0s  | `temperature` ≥ 95 °C |
| `gpu_throttle`      | gpu | throttle | warning | 30s | `utilization` ≥ 50 % AND `frequency_actual` < `frequency_max` × 0.8 |
| `npu_memory_pressure` | npu | memory | warning | 10s | `memory_used_percent` ≥ 80 |

The `gpu_throttle` rule's "while busy" guard prevents firing when the GPU is
sitting at low frequency simply because nothing is asking it to do work.
There is currently no GPU thermal rule because `xe_hwmon` is not implemented
on Panther Lake — see the GPU section above. CPU throttle detection is not
yet implemented because per-core max frequency is not exposed as a metric;
adding it is a small follow-up.

The dashboard renders active warnings as colored pills in each device section's
header (yellow = warning, red = critical with subtle pulse animation), with
the message text and "since" age in a hover tooltip.

## Process Attribution

In addition to the Prometheus metrics above, topswatch publishes a per-sample
list of processes holding accelerator devices open. This data is delivered
as the `processes` field on `/api/metrics/latest` and on the SSE stream
(it is intentionally stripped from `/api/metrics/history` to keep page-load
payloads small — the dashboard table only ever shows "now").

### GPU process attribution

- **Source:**
  - Walk `/proc/<pid>/fd/` for symlinks under `/dev/dri/`
  - Read `/proc/<pid>/fdinfo/<fd>` for each match
- **Fields used per fd:** `drm-driver`, `drm-client-id`, `drm-total-gtt`, and every `drm-cycles-<engine>` / `drm-total-cycles-<engine>` pair (one per engine the kernel exposes — typically `rcs`, `bcs`, `ccs`, `vcs`, `vecs`)
- **Busy fraction:** computed as Δ`drm-cycles-<engine>` / Δ`drm-total-cycles-<engine>` between consecutive samples. The kernel-published "total cycles" denominator means we don't need wall-time bookkeeping and the result is naturally bounded to 0..1.
- **Aggregation:** the dashboard sums per-engine fractions to a single "total busy" per process and groups by PID (one PID may hold multiple DRM clients). The top 8 processes by total busy are shown.
- **Permissions:** reading other processes' fdinfo typically requires root or `CAP_SYS_PTRACE`.

### CPU process attribution

- **Source:**
  - Walk `/proc/<pid>/stat` for every process visible
  - Field 14 (`utime`) + field 15 (`stime`) give cumulative CPU jiffies in user + kernel mode
  - Field 24 (`rss`) gives resident set size in pages
  - Page size from `os.Getpagesize()`, kernel jiffy rate from `getconf CLK_TCK` at startup
- **Busy fraction:** computed as Δ(`utime+stime`) / `CLK_TCK` / Δwall, expressed as Irix-style percent (a fully-busy single core reads 100, a 4-thread workload pegging every thread reads 400). Matches the `topswatch_cpu_cores_used` metric scaled to percent and matches `top`'s default `%CPU` column.
- **Filtering:** processes consuming less than 0.05% are dropped to keep the table short. The top 8 by CPU percent are returned.
- **Permissions:** reading `/proc/<pid>/stat` for processes outside your own UID typically requires root or the same `CAP_SYS_PTRACE` already needed for the GPU walker.

### NPU process attribution

- **Source:** Walk `/proc/<pid>/fd/` for symlinks under `/dev/accel/`
- **Fields exposed:** PID and `comm` only.
- **Why no per-process busy data:** the `intel_vpu` driver does not currently populate fdinfo with engine counters (verified empirically against kernel 6.17 during active NPU image generation — fdinfo shows only the standard `pos`/`flags`/`mnt_id`/`ino` fields even mid-workload). When intel_vpu adds fdinfo extension support in a future kernel, the same code path can pick up engine counters without changes.

### NPU PMT data path

PMT (Platform Monitoring Technology) telemetry is delivered as a binary blob
exposed at `/sys/class/intel_pmt/telem*/telem`. Each `telem*` directory has a
`guid` file; topswatch picks the entry whose GUID matches a known
NPU-telemetry GUID for the detected CPU generation. On every poll the entire
buffer is read into memory and individual registers are extracted via
generation-specific byte offset + bit range tables. Reading `telem` typically
requires root.

Register layouts, data types, and transform formulas are defined in Intel's
public PMT XML specifications at https://github.com/intel/Intel-PMT. The
frequency conversion formulas are cross-referenced against the kernel's
`drivers/accel/ivpu/ivpu_hw_btrs.c` PLL-ratio-to-DPU-frequency functions.
